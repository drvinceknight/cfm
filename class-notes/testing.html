Testing of code

Format

A group-work week. The single hour is not a lecture: students work through this topic on their own, and the session is there for you to answer questions and signpost. The deck below is questions to put to the room, not material to read out, and the reference section at the end is not delivered at all.

Open by asking what people got stuck on. If the room is silent, the minutes are the way in: ask a group what went into their questions arising box this week. That is what the box is for, and it makes the point that the minutes are useful to them rather than only to the mark.

Timing

A full session, and the last of the five group-project weeks. The hour is still questions and signposting rather than a lecture, but the deck gives it a spine for when the room has nothing to ask.

The deck

There is a write-on deck at /deck/testing/main.pdf. Slides 3 to 8 each carry a short listing, a question and a workspace for the answer the room gives. Slides 9 and 10 are filled in by each group for itself rather than by you. Answers are at the end of these notes.

What students work through on their own

  • Testing of code, and the corresponding chapter of Python for Mathematics.

Each member reports on it at the group meeting, which is the first standing item on every agenda.

Questions that come up

"How many tests do we need?" The criterion is that the tests cover all functionality of the code and the documentation, so the question to turn back on them is which function is currently untested.

"Our tests all pass, are we done?" Ask what happens at the boundaries: zero, one, an empty input, a negative where only positives were considered. The exemplary band specifically mentions edge cases the tutorial does not exercise.

"Do we need pytest?" No. Assertion statements in a test_<library>.py that runs top to bottom are sufficient and are what the example projects use.

Answers for the deck

Slide 2, the three pillars. Nothing to elicit, but it is worth thirty seconds. Modularisation, documentation and testing are the three chapters they have now read, and the Scope criterion is all three together at 50% of the project mark. Small functions are easy to test and easy to document; tests are what make documentation that is verified possible.

Slide 3, one line, two parts. After assert comes a claim that must be true, and then an optional string that is shown when it is not. Push the second part: the string is the message their future self reads when the test fails, so "The function gave the wrong answer" is weaker than a sentence naming what was expected.

Slide 4, how many tests does this need? Three, because the function does three things. Groups count functions and write one test each; the thing to count is behaviours. This is the same argument as the modularisation week from the other direction: a function that needs ten tests is probably several functions.

Slide 5, your tests all pass. Zero, one, an empty input and a negative where only positives were considered. The exemplary band asks specifically for edge cases that the tutorial does not exercise, and these four are where they usually live. Take a real function from a group in the room rather than a made-up one.

Slide 6, how do you test something random? Seeding. random.seed(0) fixes the sequence without making the function deterministic in use, so the assertion holds every run. Worth adding the second technique: for a thousand rolls you can assert the set of values obtained, or that each count falls in an expected range, which tests the behaviour rather than one draw.

Slide 7, where the tests live. A separate test_<library>.py, one function per behaviour, each with a docstring saying what it checks, and the calls at the bottom so that python test_tsp.py runs them. They do not need pytest, and the example projects do not use it. The reason to use functions rather than a flat script is that each one has somewhere to document what it checks.

Slide 8, what is a doctest for? To check that the documentation is still true. It is not where the mathematics gets tested, and using it that way makes the README unreadable. python -m doctest README.md runs them. Both are required separately: the doctests are documentation that is verified, the test file is the test suite.

Slide 9, which function is untested? This is group work, not a question to you, and it is the ten minutes of the hour that produce actions in the minutes. Walk the room. A group that cannot list its own functions has a bigger problem than testing, and that is worth knowing now.

Slide 10, the eight files. The tick boxes are for them. The useful answer is the uncomfortable one, so ask which file nobody has started. In most years that is contribution.md and the presentation, and both are cheap to start and expensive to leave.

Testing software

Discuss how we will write automated tests for the tsp library we wrote in the first section.

Writing the unit tests

Write the following in a test_tsp.py file::

import numpy as np
import matplotlib.pyplot as plt

import tsp

def test_get_tour_with_no_seed():
    number_of_stops = 4
    tour = tsp.get_tour(number_of_stops=number_of_stops)
    assert np.array_equal(tour, np.array([0, 1, 2, 3, 0]))

def test_get_tour_with_seed_0():
    number_of_stops = 4
    seed = 0
    tour = tsp.get_tour(number_of_stops=number_of_stops, seed=seed)
    assert np.array_equal(tour, np.array([0, 3, 2, 1, 0])), f"Obtained output is {tour}"

def test_get_tour_with_seed_1():
    number_of_stops = 4
    seed = 1
    tour = tsp.get_tour(number_of_stops=number_of_stops, seed=seed)
    assert np.array_equal(tour, np.array([0, 1, 3, 2, 0])), f"Obtained output is {tour}"


def test_swap_cities():
    tour = [0, 1, 3, 2, 4, 0]
    steps = (4, 1)
    new_tour = tsp.swap_cities(tour=tour, steps=steps)
    assert new_tour == [0, 4, 2, 3, 1, 0], f"Obtained output is {new_tour}"


def test_get_cost():
    distance_matrix = np.array(((0, 5, 2, 9), (5, 0, 3, 1), (2, 3, 0, 7), (9, 1, 7, 0)))
    tour = [0, 1, 2, 3, 0]
    cost = tsp.get_cost(tour=tour, distance_matrix=distance_matrix)
    assert cost == 24


def test_run_2_opt_algorithm_with_seed_0():
    distance_matrix = np.array(((0, 5, 2, 9), (5, 0, 3, 1), (2, 3, 0, 7), (9, 1, 7, 0)))
    number_of_stops = 4
    seed = 0
    iterations = 50
    tour = tsp.run_2_opt_algorithm(number_of_stops=number_of_stops,
            distance_matrix=distance_matrix, seed=seed, iterations=iterations)
    assert tour == [0, 2, 3, 1, 0], f"Obtained output is {tour}"

def test_run_2_opt_algorithm_with_seed_1():
    distance_matrix = np.array(((0, 5, 2, 9), (5, 0, 3, 1), (2, 3, 0, 7), (9, 1, 7, 0)))
    number_of_stops = 4
    seed = 1
    iterations = 50
    tour = tsp.run_2_opt_algorithm(number_of_stops=number_of_stops,
            distance_matrix=distance_matrix, seed=seed, iterations=iterations)
    assert tour == [0, 2, 1, 3, 0], f"Obtained output is {tour}"

def test_plot_tour():
    x = np.array([2, 3])
    y = np.array([2, 3])
    tour = np.array([0, 1, 0])
    plot = tsp.plot_tour(x=x, y=y, tour=tour)
    assert plot is None

test_get_tour_with_no_seed()
test_get_tour_with_seed_0()
test_get_tour_with_seed_1()
test_swap_cities()
test_get_cost()
test_run_2_opt_algorithm_with_seed_0()
test_run_2_opt_algorithm_with_seed_1()
test_plot_tour()

Run the above tests by running:

$ python test_tsp.py

Depending on time now discuss refactoring some of the code. For example:

  • Modify swap_cities to be called swap_steps as this name is more generic.
  • Possibly modify swap_cities/swap_steps so that it can handle numpy array outputs.

At each step modify the source code and then modify the tests.

Discuss importance of tests as a debugging tool.

Testing the documentation

Modify the documentation in the README.md file to use doctests::

# TSP

A library for solving instances of the travelling sales agent problem

## Tutorial

In this tutorial we will see how to use `tsp` to solve instances of the
[Travelling Salesman Problem](https://en.wikipedia.org/wiki/Travelling_salesman_problem)

Assuming we have the following distance matrix:

```python
>>> import numpy as np
>>> distance_matrix = np.array(((0, 5, 2, 9), (5, 0, 3, 1), (2, 3, 0, 7), (9, 1, 7, 0)))

```

We can obtain a tour using the following:

```python
>>> import tsp  # doctest: +SKIP
>>> tour = tsp.run_2_opt_algorithm(number_of_stops=4, distance_matrix=distance_matrix, iterations=1000, seed=0)  # doctest: +SKIP
>>> tour  # doctest: +SKIP
[0, 3, 1, 2, 0]

```

The `tsp` library includes further functionality which you can read in the
How To guides.

Note that the doctests are skipped when checked for this documentation.

Run the doc tests by typing::

$ python -m doctest README.md
